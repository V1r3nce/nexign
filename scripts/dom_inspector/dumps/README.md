# Дампы для dom_inspector

Сюда кладут снимки DOM со стенда и (по желанию) дампы сети. Дампы **коммитятся** в репозиторий:
их снимают на стенде и пушат, чтобы правки локаторов делались по факту, а не на глаз.

Каталог выбран специально: класть дампы в `tests/` нельзя (это уже вызывало нарекания),
а `tmp/` не подходит — его содержимое сносит autouse-фикстура `clear_temp_dir`.

Снимок DOM весит несколько мегабайт, поэтому держите в каталоге только актуальные дампы,
а устаревшие удаляйте: история git их всё равно сохранит.

## Как снять дамп DOM

1. Открыть на стенде нужную страницу и довести её до состояния, которое проверяем
   (открытая модалка, заполненная форма — DOM снимается ровно в этот момент).
2. В консоли devtools выполнить:

   ```js
   copy(document.body.outerHTML)
   ```

3. Вставить содержимое буфера в текстовый файл в этом каталоге — **одной строкой**.
   Имя файла произвольное, расширение не обязательно (например `need_html`).

Один файл может содержать несколько снимков. Между ними разрешено писать пометки на русском —
утилита их разбирает и показывает в отчёте:

```text
case 29:
<body ...>...</body>
case 30: (только создание договора вручную)
<body ...>...</body>
Все есть
case 31:
тут баг, скипаем: https://jira.nexign.com/browse/RMBSS-18239
```

Правила разбора:

* строка вида `case 29:`, `case: 30`, `case31:` открывает блок кейса (регистр не важен);
* строка, начинающаяся с `<body`, `<html` или `<!doctype`, считается началом снимка,
  конец — по закрывающему `</body>` или `</html>` в конце строки;
* любая другая строка — человеческая пометка; `Все есть` -> кейс готов, `Outdated` -> устарел,
  ссылка на Jira -> кейс пропускаем;
* снимок привязывается к ближайшему маркеру кейса выше; снимки до первого маркера тоже разбираются.

## Что проверяется: не только локаторы, но и бизнес-состояние

По каждому шагу отчёт печатает две вещи:

1. **что на странице** — карточка, активная вкладка, статус-теги, открытая модалка или форма.
   Это слепок состояния: по нему видно, куда тест реально дошёл, а не только что селектор нашёлся.
2. **сходится ли это с тем, что обещает шаг**. Ожидания берутся из текста самого шага:
   всё, что автор написал в кавычках, плюс статусы клиента и договора. То, на что жмут
   («Нажать 'Подписать договор'»), за ожидание не считается — это действие.

```text
шаг 3  снимок #4   ок 1/1   Договор создан в статусе 'Оформлен', клиент остался в статусе 'Потенциальный'
    на странице: карточка «Договор: 15751/2026/001052» · вкладка «Договор» · статусы: Оформлен
    ШАГ ОБЕЩАЕТ, А НА СТРАНИЦЕ НЕТ: «Потенциальный»
```

Здесь все локаторы шага нашлись (`ок 1/1`), но бизнес-ожидание не выполнилось: на карточке
договора статуса клиента нет вовсе. Такое проверкой селекторов не ловится.

Подтверждённые ожидания печатаются под ключом `-v`, неподтверждённые — всегда.

## Готовая команда: прогнать весь сьют и разобрать всё разом

```shell
.venv/Scripts/python.exe -m pytest tests/nbss/e2e_64_13_maintain_client_status --dump-dom
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps
```

Первая команда прогоняет сьют и кладёт сюда по файлу на тест. Вторая, запущенная без аргументов,
находит все дампы каталога, сама сопоставляет каждый со своим тестом (номер кейса пишется
в шапку дампа при записи) и печатает сводку — строка на тест:

```text
ПОШАГОВЫЙ РАЗБОР: дампов 26 в scripts/dom_inspector/dumps
итог: разобрано 26, с проблемами 2, без снимков 1

  ок           case 15    test_organization_transition_from_potential_to_active
  ПРОБЛЕМА     case 19    test_create_individual_with_duplicate_check              шаги 2, 3
  нет снимков  case 24    test_edit_individual_change_document_no_duplicates
```

Дальше разворачиваются только проблемные тесты — обычным пошаговым отчётом.
Код возврата 1, если хоть где-то есть проблема, — команду можно ставить в CI.

Разобрать отдельный тест из пачки: `... cli steps --test 19` или `... cli steps <файл>.txt`.

Одна оговорка: пропущенные тесты (`@pytest.mark.skip`) не выполняются и дампов не оставляют,
а бэкенд-тесты без UI пишут в консоль `[dump-dom] пропущено: страница браузера ещё не создана` —
это нормально, DOM там снимать не с чего.

## Снять DOM автоматически при прогоне

Руками копировать `document.body.outerHTML` на каждый шаг не нужно — прогон умеет писать дамп сам.
Запустите тест с ключом `--dump-dom`:

```shell
.venv/Scripts/python.exe -m pytest tests/nbss/e2e_64_13_maintain_client_status/test_client_status_transition.py     -k test_organization_transition_from_potential_to_active --dump-dom
```

После прогона в этом каталоге появится `<имя теста>.txt` со снимком DOM на каждый шаг,
и в консоли будет строка `[dump-dom] снимков записано: N -> <путь>`. Дальше:

```shell
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps <имя теста>.txt
```

Снимок делается на выходе из каждого `with allure.step(...)`, написанного в самом тесте.
Шаги внутри пейдж-объектов (декораторы `@allure.step` на методах) вложены в шаг теста
и отдельных снимков не дают — на шаг теста ровно один снимок, нумерация совпадает
с той, по которой `steps` разбирает тест.

Ключ работает и на падающем тесте: снимки, сделанные до падения, останутся в файле —
по ним видно, на каком шаге DOM разошёлся с локаторами.

## Пошаговый режим: `steps`

`check` проверяет **все** локаторы репозитория и выдаёт сотни находок. `steps` — про другое:
берётся **один** тест, и проверяются только те локаторы, до которых дотягиваются его шаги.
Отчёт короткий: зелёный шаг — одна строка, разворачивается только тот шаг, где локатор
не нашёлся или нашёлся не один раз.

Дамп для этого режима — тот же самый, что и для `check`, плюс одна необязательная строка
с номером шага перед снимком:

```text
case 15:
2
<body ...>...</body>
3
<body ...>...</body>
шаг 4
<body ...>...</body>
step 4
<body ...>...</body>
6
<body ...>...</body>
```

Правила пошаговой разметки:

* `case 15:` — как раньше: 15 это число, с которого начинается `@allure.title` теста;
* строка перед снимком с номером шага: `4`, `4:`, `шаг 4`, `step 4` — все четыре написания
  распознаются; можно вместо номера скопировать текст шага из `allure.step`;
* номер разрешено повторять: сняли на один шаг два экрана — поставьте `4` дважды.
  Локатор считается найденным, если нашёлся хотя бы в одном снимке шага;
* шаги, которые не снимали, можно пропускать: они печатаются строкой «без снимка»
  и на код возврата не влияют;
* номеров можно не ставить вообще — тогда снимки раскладываются по порядку на шаги,
  которые вообще трогают DOM (чисто API-шаги пропускаются автоматически), а в шапке
  честно пишется «нумерация шагов не указана — разложено по порядку»;
* лишние снимки не выбрасываются: они уходят в блок «лишние снимки» в конце;
* если снимки съехали на шаг (частая история — забыли снять первый экран), шаг с чужим
  снимком не красится красным поштучно: печатается одна строка «похоже, разметка снимков
  съехала» с номером снимка, где локаторы шага действительно находятся. Раскладка при этом
  не переставляется — чинить разметку дампа руками.

Запуск:

```shell
# номер кейса из заголовка теста
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps need_html --test 15

# то же самое по allure.id или по куску имени метода
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps need_html --test 902222
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps need_html --test potential_to_active

# если в дампе ровно один кейс, --test можно не писать
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps need_html
```

Тест ищется в сьюте `tests/nbss/e2e_64_13_maintain_client_status`; другой сьют или отдельный
файл теста задаётся ключом `--suite`. Номера кейсов внутри сьюта не уникальны (`21.` есть
и в ФЛ-тесте, и в OAPI), поэтому при двух кандидатах утилита печатает оба и просит уточнить.

Ключей немного: путь к дампу, `--test`, `--suite`, `--json` (машинный вывод вместо текста),
`--no-fail` и `-v` (показать ещё и найденные локаторы).

Код возврата `steps`:

* `1` — на каком-то шаге локатор не найден **или** найден больше одного раза (второе роняет
  Playwright по strict mode ровно так же, как первое). Гасится ключом `--no-fail`;
* `2` — сверять было нечего: не найден дамп, сьют или тест, дамп пуст, в нём нет ни одного
  снимка DOM или снимки не от этого кейса. В шапке отчёта тогда стоит «сверять нечего:
  снимков нет», а не «проблем нет». Ключ `--no-fail` этот код не гасит: это ошибка ввода,
  а не находка;
* `0` — проблем нет.

Пейдж-объекты теста берутся из фикстуры `setup`, а если её нет — из любой фикстуры класса
с `@pytest.fixture(autouse=True)`. Если и такой нет, обращения `self.<пейдж>.<метод>()`
не выбрасываются молча: на шаге печатается заметка разбора «нет setup-фикстуры с таким
атрибутом».

Чего в отчёте нет и не будет: локаторов, которых нет в разобранном тесте. Правится ровно свой
сьют. Локаторы из веток `if`, условие которых статически не вычисляется, красным не красятся —
для них печатается отдельная строка «лежат в невычисленной ветке if».

## Как снять дамп сети (нужен только для подкоманды `api`)

В devtools на вкладке Network: правый клик по списку -> `Copy all as cURL`, вставить в файл.
Дамп сети сейчас в основной сценарий не входит — это задел под будущие бэкенд-тесты.

Известная особенность варианта «Copy all as cURL (cmd)»: кириллица в телах запросов
теряется и превращается в пробелы. Если для бэкенд-тестов нужны настоящие значения,
снимайте через `Copy all as cURL (bash)` или сохраняйте HAR.

## Как запускать

Из корня репозитория, интерпретатором из `.venv`:

```shell
# главная команда: проверить локаторы репозитория по дампу
.venv/Scripts/python.exe -m scripts.dom_inspector.cli check scripts/dom_inspector/dumps/need_html

# если в каталоге ровно один дамп, путь можно не писать вообще
.venv/Scripts/python.exe -m scripts.dom_inspector.cli check

# только про один файл локаторов, без справочных разделов, с записью отчёта
.venv/Scripts/python.exe -m scripts.dom_inspector.cli check need_html \
    --file client_profile.py --only-problems --report report.txt --json report.json

# разбор одного теста по шагам: только его локаторы, снимок на шаг (см. раздел «Пошаговый режим»)
.venv/Scripts/python.exe -m scripts.dom_inspector.cli steps need_html --test 15

# что вообще есть на странице и где искомая кнопка
.venv/Scripts/python.exe -m scripts.dom_inspector.cli inspect need_html --search "Добавить"

# поиск идёт и по атрибутам: class, type, href, role, data-* — не только по тексту и id
.venv/Scripts/python.exe -m scripts.dom_inspector.cli inspect need_html --search ant-modal-content
.venv/Scripts/python.exe -m scripts.dom_inspector.cli inspect need_html --search submit -v

# машинный вывод повторяет человеческий: те же элементы, тот же --limit, плюс все атрибуты
.venv/Scripts/python.exe -m scripts.dom_inspector.cli inspect need_html --search Добавить --json found.json

# разбор дампа сети (задел под бэкенд-тесты, из check не вызывается)
.venv/Scripts/python.exe -m scripts.dom_inspector.cli api need_case
```

Код возврата `check`: `1`, если найдены проблемы (`--no-fail` отключает), `2` — если дамп не найден.

Полное описание ключей: `python -m scripts.dom_inspector.cli check --help`.

## Скорость

Полный прогон по дампу из 36 снимков занимает около минуты: 2525 уникальных селекторов
гоняются по каждому снимку. Если нужен быстрый ответ по одной странице, ограничьте снимки —
это единственный ключ, который реально сокращает работу (`--snapshot 2` даёт ~1.5 секунды):

```shell
.venv/Scripts/python.exe -m scripts.dom_inspector.cli check need_html --snapshot 2 --case 29
```

Ключи `--class`, `--file`, `--module`, `--attr` фильтруют то, что печатается в отчёте,
но не сокращают прогон: покрытие владельца (по нему отличается «сломанный локатор»
от «страница не из этого дампа») считается по всему репозиторию.

## Что значит «страница не в дампе»

Дамп снят с одной-двух страниц, а локаторов в репозитории под три тысячи, поэтому основная
масса из них не находится просто потому, что их страницы в дампе нет. Такие локаторы получают
статус `page_not_in_dump`, в проблемы не выносятся и перечислены отдельным справочным разделом
**«СТРАНИЦЫ, КОТОРЫХ НЕТ В ДАМПЕ»** — по файлам и классам, с числом пропущенных локаторов
и покрытием. В JSON это ключи `pages_not_in_dump` и `pages_not_in_dump_total`.

Присутствие страницы оценивается по лучшему из трёх покрытий: файл в снимке, класс-владелец
в снимке, класс-владелец по дампу целиком. Файла одного мало: `client_profile.py` — это сразу
и карточка клиента, и форма редактирования, и вкладки. Плюс отдельное правило: если у селектора
есть точный якорь (`#id`, `[data-testid=...]`, `@id='...'`) и этот якорь в дампе встречается,
локатор всегда считается сломанным (`not_found`), каким бы ни было покрытие.

Проверить отфильтрованные локаторы всё равно:

```shell
.venv/Scripts/python.exe -m scripts.dom_inspector.cli check need_html --coverage 0
```

## Ограничение поиска `inspect --search`

Поиск идёт по индексу опознаваемых элементов снимка: текст, `id`, `data-testid`, `name`,
`aria-label`, `title`, `placeholder`, `value`, подпись из `<label>` и **все** атрибуты
(`class`, `type`, `href`, `role`, `data-*`). Обычные `div`/`span` без id, без текста и без
интерактивности в индекс не попадают, поэтому подстрока из такого узла в списке не появится.
Чтобы ноль нельзя было принять за факт, утилита всегда считает вхождения подстроки в сыром
HTML снимка и говорит прямо: «настоящий ноль» либо «ложный ноль» с подсказкой про `grep`.
